主题：行业应用（智能助手与效率工具方向）\nP12: 作品简介\nP13: ClawAssistant 是一款面向高校学生与年轻用户的多功能 Web 智能助理。它以大模型 Agent 为核心，把天气查询、信息检索、课表管理、任务提醒、旅行规划、文件处理、图片与语音生成、角色定制这些能力统一到一个自然语言入口里。\nP14: 和普通聊天机器人不太一样的地方在于，我们想解决的是需要连续操作的真实任务，而不只是回答一个问题。用户描述目标之后，助手会自己判断任务类型、决定要不要调用工具、调用哪个工具，同时把模型推理信息、工具调用过程和执行结果用时间线展示出来。这样用户拿到结果的同时，也能看清楚结果是怎么来的。\nP15: 作品来源：自主设计与开发\nP16: 应用行业：教育信息化、个人效率工具、生活服务\nP17: 数据来源\nP18: • 公开第三方 API：WeatherAPI（天气）、Tavily（搜索）、腾讯地图、阿里云百炼（图片与语音）\nP19: • 用户本地数据：SQLite 存储对话、任务、课表、订阅等结构化数据\nP20: • 大模型生成内容：对话回复、推理信息、图片、语音\nP21: 作品展示\nP22: 本地部署 Web 应用（http://localhost:8080）。后端 Spring Boot 3.3.2 + Java 21，前端 React 18 + TypeScript + Vite。\nP23: 正文\nP24: 一、选题定位\nP25: 1.1 行业背景与痛点\nP26: 大模型这两年发展很快，但落到日常使用时还是有几个绕不开的问题。\nP27: 第一，通用模型什么都能聊，但落到具体事上就差点意思。问它「这周有什么考试」，它没法直接给课表，因为没有接入用户数据。第二，AI 给出的结果没法验证来源。它到底是查了实时数据还是凭记忆回答的，用户看不出来，涉及日程提醒这类操作时就不太敢用。第三，完成一件事往往要在好几个 App 之间来回切换，每个 App 的操作逻辑还不一样，效率反而低了。\nP28: 1.2 选题意义\nP29: 我们希望解决的不是「让 AI 能回答更多问题」，而是让它能够真正参与任务的完成。所以项目重点放在任务理解、工具调用和多轮执行上，让用户只需要描述目标，助手就可以继续完成后续操作。同时，我们把推理信息和工具调用链路展示出来，让用户不仅能拿到答案，也能知道这个答案是怎么来的。\nP30: 1.3 项目特色\nP31: 做这个项目的过程中，我们主要在以下几个方面做了尝试：\nP32: （1）混合式意图路由。我们没有只用关键词或者只用大模型来判断用户意图，而是叠了好几层：先看有没有显式切换，再处理待确认状态，然后关键词触发、向量语义匹配，最后才让大模型兜底分类。这样比单一方式更稳。而且一个输入可以同时激活多个技能，比如「下雨天怎么去机场」会同时命中天气和交通。\nP33: （2）可持续执行的 Agent 运行时。助手不是回答一句就结束，而是围绕用户目标持续推进。我们用 ReAct 循环配合结构化计划，计划里的任务有依赖关系，系统会用拓扑排序检查有没有循环依赖，避免任务卡死。中间状态会存起来，失败了可以从断点继续。\nP34: （3）可治理的长期记忆。我们没有把对话历史直接堆进上下文，而是做了一套记忆生命周期：自动提取候选记忆、去重、合并、向量化存储。召回时按语义相似度、重要性、置信度、新鲜度加权打分，过期或超容量时自动淘汰。用户还能手动编辑和撤销记忆。\nP35: （4）人机协同安全执行。删除文件、创建提醒这类高风险操作，系统不会让模型直接执行，而是先暂停，弹一个确认卡片给用户。用户确认后执行的是原始的工具调用，不是让模型重新生成一次，避免参数漂移。\nP36: （5）可观察、多模态、可主动服务。文本、图片、音频、文件都统一走 Artifact 工作流管理。执行过程通过 SSE 实时推到前端，用户能看到当前用了哪个技能、调了哪个工具、花了多久。另外通知系统做成了持久化的，定时任务触发后先写入 outbox，在线用户实时收到，离线用户下次登录也能看到。\nP37: 二、社会价值\nP38: 2.1 目标用户与场景\nP39: 核心用户是高校学生和年轻职场人。学生的日常任务特别碎——课程、考试、竞赛、查资料、安排日程、查天气，这些事分散在不同平台上。ClawAssistant 用自然语言做统一入口，把原本要切好几个 App 才能做完的操作串成一个连续任务，减少来回切换的成本。比较典型的场景有：\nP40: • 学习辅助：查课表、设考试倒计时、搜资料、做学习计划\nP41: • 生活服务：查天气、规划出行、追番提醒、节假日查询\nP42: • 效率提升：文件管理、定时任务、目标追踪\nP43: • 内容创作：生成图片、合成语音、写文案、做旅行方案\nP44: • 情感陪伴：通过角色定制创建专属 AI 人设，用克隆音色对话\nP45: 2.2 价值与可推广性\nP46: 我们希望用户在使用 AI 时，不仅能拿到答案，也能知道这个答案是怎么来的。比如查天气时，可以看到天气工具是否被调用、返回了什么数据；规划旅行时，可以看到助手如何逐步获取信息、计算预算、生成方案。这种透明度能让用户更放心地使用 AI 来完成实际任务。\nP47: 在扩展性方面，每个场景都做成了独立技能。新增场景时，在现有技能框架下注册技能和工具即可，核心的执行流程不需要重复开发。后续可以比较方便地扩展到医疗咨询、法律服务、企业办公等领域。\nP48: 三、技术方案\nP49: 3.1 总体架构\nP50: 整个系统分四层，从下到上是基础设施层、模型层、智能体层和交互层。各层之间用标准接口连接，替换某一层不会影响其他层。\nP51: \nP52: 基础设施层用 Spring Boot 提供 Web 服务，SQLite 存结构化数据，Qdrant 做向量检索。模型层对接阿里云百炼的 Qwen 系列，用它的原生 Function Calling 和流式输出。智能体层是核心，ReAct 循环负责「思考-行动-观察」的迭代，技能路由把请求分到对应场景，工具框架统一管理工具集合。交互层用 React 渲染对话界面、推理时间线和工具调用状态。\nP53: 3.2 核心执行机制\nP54: 用户输入任务后，首先经过技能路由判断属于哪个场景，加载对应的提示词和工具集合，然后进入 ReAct 执行循环：\nP55: 用户目标 → 技能识别 → 任务理解 → 工具选择 → 工具执行 → 结果观察 → 再次决策 → 最终回复\nP56: \nP57: 助手不是生成一段文本就结束，而是围绕用户目标持续执行任务。先理解任务意图，通过技能路由加载对应能力，然后在 ReAct 循环里反复进行「决策—执行—观察」，判断任务完成后才输出最终回复。如果没完成，就根据工具返回的结果重新决策，进入下一轮。\nP58: 技能路由维护了用户当前的任务状态，支持激活新技能、继续当前任务、切换技能、退出技能，以及同时激活多个技能。所以用户可以自然地说「帮我规划旅行」「预算降低一点」「换个目的地」「算了先查天气」，系统不会把每句话都当成独立请求，而是理解为一个持续的任务过程。\nP59: 举个例子，用户说「帮我规划一次上海三日游，预算每人 2500 元，希望安排经典景点和美食」。助手不会直接写一篇攻略，而是会先检查信息够不够——如果用户没说出发日期，就先问清楚；然后依次查天气、找景点、规划交通、算预算，最后生成几套方案让用户选。用户选完之后如果想改，比如把第二天的博物馆换成迪士尼，助手会根据修改重新调整行程和预算。\nP60: 这里有一个我们开发时遇到的真实问题：最开始测试旅行规划时，发现模型有时候在缺少出发地、日期等关键信息的情况下，就直接生成了完整方案。后来我们在旅行技能里加了需求收集的规则，再配合回复守卫检查关键工具是否真正执行，才避免了模型跳过必要步骤的情况。\nP61: 3.3 关键技术设计\nP62: 大模型选用阿里云百炼 Qwen 系列，主要因为两点：一是原生支持 Function Calling，工具调用的协议和我们的设计比较契合；二是推理模式下会输出独立的 reasoning_content，给推理可视化提供了数据基础。\nP63: 技能路由用了多层触发。先用关键词做快速匹配，命中高置信度场景就直接路由；没命中的话用向量语义匹配——我们给每个技能准备了代表性示例，生成向量后和用户输入算余弦相似度；最后才交给 LLM 做语义判断。多个技能同时达到高置信度时会并行激活。每个技能有自己的提示词、工具集和回复守卫，互不干扰。\nP64: 工具调用框架把所有工具统一成一个接口，用 JSON Schema 描述参数，模型按描述自己决定调哪个、传什么参数。目前实现了 36 个工具，覆盖 12 个功能域，重点不在数量，而在助手如何根据任务状态动态选择和组合它们。\nP65: 计划和依赖管理方面，模型可以返回结构化的任务计划，系统会把计划转成 PlanState，校验任务数量、检查 ID 是否重复、依赖任务是否存在，还用拓扑排序检测有没有循环依赖。校验通过后持久化，再按未完成任务继续执行。这样长任务可以分解成有依赖关系的子任务，中间状态会保存，失败了能从断点继续。\nP66: 高风险操作走人机协同确认。删除文件、修改文件、创建提醒这些操作，系统识别到后会先保存一个待执行动作，前端弹确认卡片。用户点确认后，执行的是原始的工具调用，不是让模型重新生成，避免参数漂移。确认状态会持久化，还有过期处理和用户取消。\nP67: 长期记忆用 Qdrant 存向量，但不是简单存进去就完了。我们做了完整的记忆生命周期：从对话里自动提取候选记忆，分类和主题解析，向量化后检索相似记忆，让 LLM 判断是新增、更新、合并还是重复。召回时按 0.70×语义相似度 + 0.15×重要性 + 0.10×置信度 + 0.05×新鲜度 打分排序。容量超了或者记忆过期了，按 0.50×重要性 + 0.20×置信度 + 0.30×新鲜度 淘汰低分的。用户还能手动编辑、停用和撤销记忆。\nP68: 上下文管理方面，我们没有把全部历史消息无上限地塞进模型，而是用对话摘要、上下文预算、Token 估算、历史轮次裁剪来动态构建当前上下文，再按需召回长期记忆。这样长对话也不会把上下文撑爆。\nP69: 流式响应用 SSE。正文逐字推送，工具调用的开始和结束也实时推送。模型输出的推理信息单独走一条事件通道，前端做成可折叠的时间线，默认只显示摘要，用户可以主动展开看。\nP70: 多模态内容统一走 Artifact 工作流。图片、音频、PDF、文档上传后由 ArtifactService 管理，按用户隔离存储，通过 request-scoped 的 ArtifactCollector 回传到当前对话。前端有图片看板、文件预览、生成过程展示，生成结果会聚合展示。\nP71: 通知系统做成了持久化主动服务。定时任务、课程提醒、考试提醒触发后先写入 notification_outbox，在线用户通过 SSE 实时收到，离线用户下次登录仍能看到，还能按用户设置走邮件旁路通知。\nP72: 3.4 开发中遇到的问题与处理\nP73: 问题一：大模型生成的工具参数有时候格式不对或者缺字段，直接执行会导致任务中断。我们用 JSON Schema 对参数做约束，加上校验、重试和降级。多次失败后把错误转成模型能理解的结果，让它重新决策，而不是直接把对话断掉。\nP74: 问题二：如果把所有工具和提示词同时给模型，上下文会变长，模型也容易选错工具。我们用技能路由先确定当前任务属于哪个技能，只注入这个技能对应的提示词和工具，按场景动态加载。\nP75: 问题三：复杂任务不是一次工具调用能完成的，需要好几轮「决策—执行—观察」。我们用 ReAct 循环保存当前任务上下文，根据工具返回结果决定下一步，让任务能持续推进到结束。\nP76: 问题四：向量库、天气 API 这些外部服务可能因为欠费、限流或者网络问题用不了。我们把它们做成可选依赖，不可用时自动降级并打日志，保证对话还能用。\nP77: 四、功能展示\nP78: 下面挑几个能体现多步骤任务执行的场景具体说明。\nP79: 4.1 多步骤旅行规划\nP80: 旅行规划是最能体现助手执行能力的场景。用户不用填表，只要说清楚想去哪、玩几天、预算多少，助手会自己判断信息够不够，不够就问，够了就一步步执行。\nP81: 示例：上海三日旅行规划\nP82: 用户输入：「我和朋友两个人准备从北京去上海玩三天，预算每人 2500 元，希望以经典景点和美食为主。」\nP83: 执行过程：\nP84: 和直接生成一篇攻略不同，这个过程是可以持续推进和修改的。用户中途改主意，助手会根据当前已有的信息继续调整，而不是从头再来。\nP85: 4.2 对话与推理过程展示\nP86: 这是最基础的交互。用户发一句话，助手通过 ReAct 循环处理。模型输出的推理信息以可折叠时间线显示，默认只显示摘要，点开能看完整内容。工具调用的状态也会实时显示：运行中是转圈，成功是对勾，失败是叉号并显示错误详情。\nP87: 4.3 角色定制与声音克隆\nP88: 这个功能让用户可以创建自己的 AI 角色，不只是文字上扮演，连声音都能克隆。\nP89: 创建角色时可以填头像、名称、性格、背景故事、说话风格、口头禅。信息越丰富，AI 对话时的人设越稳定。比如创建一个「奶奶」角色，填好「慈祥、爱唠叨、总担心孙子吃不饱」这样的性格，以及具体的背景故事，AI 回复时就会一直保持这个人设。\nP90: 音色方面有两种选择：一是用系统预设的 6 种音色（阳光大男孩、欢脱元气女、天真女童等），二是上传一段 3 到 10 秒的录音做声音克隆。克隆成功后，AI 就会用这个专属音色说话。底层用阿里云百炼的 CosyVoice 系列，预设音色走 cosyvoice-v3-flash，克隆音色走 cosyvoice-v3.5-plus。\nP91: 用户还可以点「试听声音」预览效果。在对话中选择某个角色后，AI 回复会自动带上这个角色的人设和音色。\nP92: 4.4 天气与实时搜索\nP93: 天气调 WeatherAPI，能自动识别城市名。搜索用 Tavily，主要回答实时性的问题，比如「今天有什么新闻」，弥补模型知识截止的问题。工具返回的原始数据会经过模型整理后再呈现给用户。\nP94: 4.5 文件管理与定时任务\nP95: 文件管理支持生成、保存、读取、搜索、更新、删除、列表，读取时能解析 PDF、Word、Excel。定时任务支持自然语言解析时间，存在 SQLite 里，重启不丢。\nP96: 4.6 校园服务与动漫追番\nP97: 校园服务包括课表导入、考试提醒、竞赛和招聘信息推送。动漫追番可以订阅新番，上线时自动提醒。这些都是围绕学生场景做的。\nP98: 4.7 图片与语音生成\nP99: 图片生成调阿里云百炼，语音合成把文字转成语音播放，都是一句话触发。\nP100: 五、技术实现细节\nP101: 5.1 技术栈\nP102: 5.2 安全设计\nP103: • JWT 认证：登录后签发 Token，请求带 Token 校验\nP104: • 输入校验：用户输入统一转义，防注入\nP105: • 密钥管理：第三方 API Key 走环境变量，不写进代码\nP106: • 数据隔离：用户数据按 user_id 分开存\nP107: • 高风险操作确认：删除、修改等操作需用户确认后才执行\nP108: 六、核心能力\nP109: 项目的重点不在工具数量，而在助手能不能理解用户目标、选对技能、把工具组合起来用，并且把整个过程清楚地展示给用户。\nP110: 七、总结与展望\nP111: ClawAssistant 这个项目，我们想做的不是一个功能更多的聊天机器人，而是让大模型能够真正参与任务的完成。目前已经实现了以 ReAct 为核心的多工具协作，配合混合式技能路由、结构化计划、长期记忆治理、人机协同确认、执行过程可视化、角色定制和通知系统，形成了从用户输入到任务完成的完整链路。\nP112: 简单说，它不是一个「会聊天的机器人」，而是一个能理解上下文、持续完成任务、记住用户偏好、调用真实工具并主动提供服务的可解释个人 Agent。\nP113: 后续打算往三个方向继续做：\nP114:
